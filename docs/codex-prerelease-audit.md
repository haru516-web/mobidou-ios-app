## 目的

もび道（Expo / React Native iOS アプリ + Cloudflare Workers/D1 サーバー）を本公開する前に、**公開後に問題になりうるものを一つ残らず洗い出し、直せるものは直し、直せないものは「誰が・何を・どうやって」閉じるかを明示した公開前チェックリストを完成させる**。

「たぶん大丈夫」で閉じない。各項目は **確認方法・結果・証跡（コマンド出力 / ファイル:行 / 画像）** を書いて初めて「確認済み」にする。確認できないものは正直に「未確認（理由）」「要人手」と書く。

## 確認する領域（全て実施）

### A. コード品質ゲート
1. `npm run typecheck`、`npm test`（ルート）、`server/` のテスト・typecheck を実行し結果を記録。
2. `npx expo-doctor`（可能なら）、`npx expo config --type public` で設定の健全性確認。
3. `npm audit --omit=dev`（ルート・server）。重大な脆弱性の有無と対処方針。
4. TODO / FIXME / HACK / `console.log` / デバッグ用フラグ / サンプル・見本データ / `localhost` / テスト用URL・ID / 仮のTeam ID・D1 ID・商品ID が本番ビルドに残っていないか `rg` で全検索。
5. 未使用の巨大アセット・容量（ビルドサイズ）、`.gitignore` 漏れ（秘密・生成物・`output/`・`.claude/` 等がコミット対象でないか）。

### B. 秘密情報・設定
1. リポジトリ全体（履歴含む `git log -p` の検索可能な範囲）に API キー・トークン・秘密鍵・Apple 証明書・`.env`・Cloudflare 資格情報が無いか。
2. `app.json` / `app.config.js` / `eas.json`: bundleIdentifier、version / buildNumber、deployment target、権限文言（NSHealthShareUsageDescription 等）、entitlements、ウィジェット target の Team ID、Associated Domains、ATS 設定、Privacy Manifest（`PrivacyInfo.xcprivacy`）の有無と Required Reason API の宣言。
3. `server/wrangler.toml`: D1 の database_id が実IDか、本番/試験の分離、必要な secret / vars 名が README と一致するか、`APPLE_BUNDLE_ID` 等の整合。
4. アプリ側が参照するサーバー URL が本番を向き、HTTPS で、開発用 URL が残っていないか。

### C. 課金・ガチャ（最重要）
1. IAP 商品 ID・価格・表示が、アプリ内表示 / サーバー設定 / App Store Connect 記載予定値で一致するか（`tests/legalPrices.test.ts` の範囲外も確認）。
2. 購入フロー: 二重付与・途中失敗・キャンセル・保留・再送・復元・返金の扱いを**コードを読んで**状態遷移として整理し、穴を列挙（`src/services/purchase*`、`server/src/worker.ts`、`store.ts`、`crypto.ts`）。
3. 確率表示（景表法）: アプリ内表示の割合と実抽選ロジックが一致するか。天井・無料/有償・イベントプールの扱い。数値を計算で照合する。
4. サーバーでの JWS 検証、リプレイ防止、ユーザー単位認可、入力検証、レート制限、エラー時にログへ秘密が出ないか。
5. 特商法表記（`legalNotice.ts`）、利用規約、プライバシーポリシーへの導線がアプリ内（設定・購入画面）から到達できるか。

### D. プライバシー・データ・アカウント
1. 実際にサーバーへ送信されるデータを**コードから棚卸し**し（送信項目・目的・保持）、`privacy-policy.md` / `privacyPolicy.ts` / `app-store-privacy.md` / アプリ内の説明文 / Info.plist 文言と矛盾が無いか全て突き合わせる。「送信しない」等の古い文言が残っていないか。
2. アカウント削除: アプリ内から開始でき、サーバーの関連データが消え、再送で復活しないか（`tests/accountDeletion.test.ts` と実装を確認）。
3. HealthKit: 読み取りのみか、用途説明、拒否時の挙動、手入力データの除外、広告・第三者提供をしていないこと。
4. 子ども・年齢レーティング回答の根拠（ガチャ・課金・ランダム商品・UGC・フレンド）。

### E. ソーシャル・UGC・公開ゲーティング
1. フレンド / ギフト / チーム / 通知など他人と関わる機能を洗い出し、各機能が**本番で有効か無効か**、サンプル・ローカルのみ動作の機能が本番で本物に見えて混乱を生まないか確認。
2. 他人に表示される文字列（名前等）の通報・ブロック・不適切語対策（Apple 1.2）が必要な範囲で存在するか。
3. 未接続・「準備中」の導線が本番に残っていないか（残すなら審査説明と一致するか）。

### F. UI / 実機品質（コードと既存スクリーンショットから確認できる範囲）
1. 全画面が縦スクロール無しで収まる方針（PagedBody / FitToHeight）に反する画面が無いか。主要サイズ（375x667 / 390x844 / 430x932）で `docs/QA.md` の手順を確認。
2. 仮置き（プレースホルダ）デザイン・仮文言・仮画像・誤字・未翻訳が無いか。画面内の全日本語文言を `rg` で収集し、誤字・不統一・不適切表現を確認。
3. アクセシビリティ（文字拡大・VoiceOver ラベル・視差低減）の最低限の対応。
4. 起動・初回体験・オフライン時の挙動（無限待ち・クラッシュ要因となる未処理例外）をコードで確認。

### G. アセット・ライセンス・コンテンツ
1. 音声 / 画像 / フォント / ライブラリのライセンス・クレジット（`docs/audio-credits.md`、フォント OFL 等）がアプリ内クレジットまたは設定に反映されているか。生成物の権利に関する懸念点の列挙。
2. 実在の神社・名称・固有名詞を使う箇所の表記・権利上の注意（誤情報・宗教的配慮・商標）。
3. アプリアイコン / スクリーンショット（`docs/app-store/`）が現行 UI と一致し、App Store 要件のサイズ・形式か。

### H. App Store Connect 提出物
1. 提出メタデータ（名称・サブタイトル・説明・キーワード・サポート URL・プライバシーポリシー URL・年齢レーティング・審査メモ・デモ手順）の下書きが揃っているか。無ければ `docs/app-store/` に作成。
2. サポート / プライバシー / 規約 URL が実際に到達可能か（サーバーの該当エンドポイントを確認。到達確認できない場合は理由を記載）。
3. 審査者向けメモ: 課金テスト手順、HealthKit の説明、アカウント不要である旨など。

### I. サーバー運用
1. 本番デプロイ手順（`release-deploy-steps.md`）が現行実装と一致するか、実際に上から追って抜けを確認（マイグレーション順、secret 設定、cron / スケジュール、20:00 JST 同期）。
2. コスト暴走対策（レート制限・上限・無駄な書き込み）。サーバー費用は最小限・所有者負担の方針。
3. バックアップ・復旧・監視・障害時の販売停止手順の有無。

## 進め方・ルール

- **読み取り・検査を優先**。直してよいのは「明白なバグ・誤字・古い文言・設定ミス」で、変更は最小限、変更ごとに理由を記録。仕様判断が要るもの（価格・確率・文言の方針・見た目の変更・機能の有効/無効）は**変更せず**「要判断」として提示する。
- 既存の見た目（和紙調デザイン）を勝手に変えない。Mobby を隠す・置き換える等もしない。
- 秘密情報は出力・コミットしない。見つけたら値を書かず場所だけ報告。
- 実機・App Store Connect・本番 Cloudflare・法律家確認など**Codex では確認できないもの**は捏造せず、「要人手」として手順付きで列挙する。
- 同じ失敗が2回続いたら方法を変える。
- コミットは分け、メッセージに何を直したか書く。`git push` はしない。
