# イベント巡礼 実装計画（第一回：リリース同時展開）

作成 2026-10-08。基本方針は `design-v3-monetization-server.md` の §2・§6、コスト方針は memory `server-cost-minimal`。ここで決めた内容が設計書と食い違う場合は、この文書を優先する。

## 1. 決定事項

| 項目 | 決定 |
|---|---|
| 参加条件 | **ソロ不可**。2〜4人のチームでのみ参加できる（イベントごとに最小・最大人数を持つ。第一回は 2〜4） |
| フレンド | チームはフレンドと組む。足りなければ**招待リンク/コードで友人にアプリを入れてもらう**（ユーザ増加の導線）。参加と同時に作成者とフレンドになる |
| 進み方 | チーム全員の歩数の**合計**でイベントマップを進める |
| ゴール距離 | **人数に関係なく固定**（2人でも1か月でクリアできる水準。人数が多いほど早く着く） |
| 報酬 | チームがクリアしたら**参加者全員**が受け取る。二重受取は (user, event, reward) の一意制約で防ぐ |
| 歩数データ | 日別履歴は持たない。**1人1行**（合計・最終送信日・その日の値）。画面に出すのはチーム合計と各メンバーの合計歩数のみ |
| スポット | **すべて架空**の社・祠。実在の神社仏閣・実在の車種/メーカー/ロゴ/通信会社名は使わない |
| 期間 | 約1か月。クリア後の周回は第一回では行わない（詳細は後で決める） |
| 歩数の送信 | 1日1回、当日20:00〜翌日20:00（JST）の窓（既存 `src/services/eventSteps.ts`） |

## 2. テーマ「時代をたどる巡礼」（第一回）

- 題名案：**「時をめぐる道」**。昭和から平成へ、時代の宝物（ミニチュア）を祀る架空の社を巡る。
- 昭和旧車ブーム・平成レトロ・ガラケーは**ミニチュア（奉納品）**として扱い、社は架空の立ち寄り先にする。
- ヤンキー・暴走族の要素は、迷惑運転の美化を避け、昭和レトロの文化（改造車の集い、リーゼント、ラジカセ）として明るく描く。未成年も遊ぶので審査・年齢区分に配慮する。
- 登場物はすべてオリジナルデザイン。商標になりうる名称・ロゴ・型番は使わない。

|---|---|---|---|---|
| 1 | 昭和 | ひだまり商店街の小社 | ブリキの丸目セダン | 30,000 |
| 2 | 昭和 | 峠の見晴らし祠 | 角ばったクーペ | 70,000 |
| 3 | 昭和 | 夜明けドライブインの社 | ロングノーズの流線型スポーツカー | 110,000 |
| 4 | 昭和 | 銭湯煙突山の祠 | 黒電話 | 150,000 |

名前・数値は仮。コンテンツ確定後に `src/data/events.ts` を書き換えるだけで済むようにデータ化する。

## 3. サーバの負担（Cloudflare D1）

チームの人数は負担にほぼ効かない。増えるのは参加者の総数だけ。

| 操作 | 頻度 | D1の行数 |
|---|---|---|
| 歩数送信（1行を更新） | 1日1回 | 書込み1行 |
| 画面を開く（チーム合計＋メンバー） | 1日数回 | 読込み最大4行 |
| クリア報酬の受取 | 期間中1回 | 書込み1〜2行 |

- 無料枠（書込み10万行/日、読込み500万行/日）で参加者が約2〜3万人まで収まる。超える場合は Workers 有料プラン（月$5）。
- 容量は1人あたり約100バイト。10万人でも約10MB。
- 状況取得は端末側で数時間キャッシュ。マップ画像は同梱。ポーリングはしない。

## 4. データ設計（既存スキーマの変更点）

`events` はそのまま。`event_teams` / `event_members` / `event_steps` を次のように調整する。

- `events`: `min_members`, `max_members`, `goal_steps` を追加（イベントごとに人数制限と固定ゴールを持つ）。
- `event_teams`: `invite_code`（一意）, `status`（`recruiting` / `active` / `cleared`）, `started_at` を追加。
- `event_members`: 既存のまま（主キー event_id×user_id＝1人1チーム）。
- `event_steps`: **主キーを (user_id, event_id) にして1人1行**。`total`（累計）, `day`（最終送信日）, `day_value`（その日の送信値）, `updated_at`。
  - 送信時：同じ日なら `total += 新しい値 − day_value`、新しい日なら `total += 新しい値` として `day_value` を置き換える。
  - 1日の上限（イベント用は30,000歩/人を想定）を超えた分は切り捨てる。
- `event_claims`（新規）: (user_id, event_id, reward_id) 一意。報酬の二重受取防止。
- 人数の上限・クリア判定・報酬の付与はすべてサーバ側で行う。アプリは結果を表示するだけ。

### API

| 用途 | エンドポイント |
|---|---|
| イベント一覧/状況 | `GET /events/current` （開催中のイベント、自分のチーム、メンバーの合計歩数、合計） |
| チーム作成 | `POST /events/:id/teams` → 招待コードを返す |
| 招待で参加 | `POST /events/join { code }` → 参加と同時に作成者とフレンドになる |
| チーム開始 | `POST /events/:id/teams/start`（min人数以上で作成者が実行） |
| 歩数送信 | `POST /events/:id/steps`（既存。1行更新に変更） |
| 報酬受取 | `POST /events/:id/claim`（クリア後。参加者全員が1回ずつ） |
| 離脱 | `POST /events/:id/leave`（募集中のみ。開始後は離脱しても歩数は残る） |

## 5. アプリ（UI）— イベントモードの方針（2026-10-08 決定）

巡礼選択画面は現在なく、巡礼は固定順で進む。そのため、イベントは**独立した画面を足すのではなく、各タブの「イベントモード」に切り替える**形にする。イベントボタンは既存の PopButton（浮遊する和紙の丸い印）と同じ作りにする。

| 画面 | イベントの入口 | 切り替わる内容 |
|---|---|---|
| ホーム | キャラクターの**左側**に、ふわふわ浮遊するイベントボタン | **イベント本画面**（参加前/募集中/チーム状況/報酬受取。下記 §5.1）へ遷移 |
| 御朱印帳 | **左上**にイベント御朱印帳ボタン（右上の目次ボタンの反対側） | イベント御朱印帳を閲覧（イベント専用の表紙と御朱印） |
| ガチャ | 画面の空いているところにイベントガチャボタン | イベント限定ガチャ（展開予定。第一回では入口のみ、中身は後で決める） |
| おでかけ | 今日の歩数カードの**左側**に、右側の絵図ボタンと同じ見た目のイベントボタン | おでかけ画面がイベント専用に切り替わる。歩数画面は**チーム合計**の歩数、絵図ボタンでは**イベント専用マップ**。モード中は同じ場所に「通常」ボタンが出て、押すと通常のおでかけ画面に戻る |
| コレクション | 上部の「コレクション」の文字を**削除**し、その場所にイベントボタン | イベント専用のコレクション画面（展示室・御朱印・ミニチュアなどの構成は通常と同じ。中身がイベントのもの）。モード中は通常に戻すボタン |

- 現在の `PilgrimagePicker`／`EventSlot` の接続は到達できないので、実装時に外す（`EventScreen` と `eventTeam*` は再利用する）。
- イベント本画面（§5.1）はホームのボタンからだけ開く。他タブのボタンはモード切り替えと、そのタブ内の閲覧。
- 参加前（チーム未作成）のときは、他タブのイベントボタンも本画面へ誘導する（「まずチームをつくろう」）。
- 画面はスクロールさせず `PagedBody` で収める。和紙調の既存コンポーネントのみを使う。
- ローカルで先に作る：サービス層を差し替え可能にし、**ローカルのモック**（メモリ上）で全状態を動かす。サーバ接続は後で同じインターフェースの実装を足す。

### 5.1 イベント本画面（ページシート、実装済みの下書き）
- 参加前：イベントの紹介、報酬、人数ルール、「チームを作る」「招待コードで参加」。
- 募集中：チームメンバー、招待リンク/コードの共有、人数が足りれば「出発する」。
- 巡礼中：イベントマップ（合計歩数と次のスポット）、各メンバーの合計歩数、ミニチュアの集まり具合。
- クリア：報酬（イベント限定の木札・ミニチュア・御朱印）の受取。

### 5.2 画像アセット
Codex に依頼する。内容と仕様は `docs/codex-event-assets.md`、作業ブランチは `codex/event-assets`。

## 6. 公開前に必須の作業

- ソーシャル機能（フレンド・プロフィール・招待）の公開ゲートを外す（memory `pre-release-social-gating`）。名前の不適切表現対策を入れる。
- 招待リンク（ユニバーサルリンク/カスタムスキーム）でアプリ未導入の友人を App Store に誘導し、インストール後にコードを引き継ぐ流れの確認。
- イベント画像（社・ミニチュア・地図）はCodex向けの素材プロンプトを別途作る。
- 年齢区分・課金上限は影響を受けない（イベント参加は無料）。報酬の木札は既存の元帳に記録する。

## 7. 実装の順番

1. 計画書（この文書）
2. ローカルUI＋モック（`src/data/events.ts` の拡張、`src/services/eventTeam.ts` のインターフェースとモック、イベント画面、イベント枠）
3. 単体テスト（進行度・状態遷移・人数制限・報酬の判定）
4. サーバ（スキーマ、API、テスト）→ アプリと接続
5. 素材差し替え（Codex）→ 実機確認 → 公開ゲートの確認
