## プロンプト4: サーバーのガチャを、アプリの規則に合わせる

```
あなたは「もび道」のバックエンド担当です。ブランチ codex/v3-followups で作業してください。
触ってよいのは server/ だけです。アプリ本体（src/、App.tsx など）は変更しません。

## 背景
server/ のガチャ（POST /gacha/pull）は、重み付き・レア度・「全ガチャ回数」による天井という仮の仕様で作られています。
確定した仕様は次のとおりで、基準の実装とテストは src/services/gacha.ts と tests/gacha.test.ts にあります。まず読んでください。

## 確定した仕様
- 対象は、モビー全体（src/petCatalog.ts の全ID、いまは18体）から**完全に均等**。最初の1体・重複も含めて、同じ確率。レア度・重みは使わない。
- 最初のモビー（1体）は、初回にプレイヤーが選ぶ。それ以降はすべてガチャ。
- 無料ガチャ: 各巡礼の**初回結願**で1回。同じ巡礼では、二度と付与しない（ユーザー×巡礼IDで一意）。無料ガチャは**1回ずつ**しか引けない（5連は有償のみ）。
- 有償ガチャ: 1回と、5連（5回連続の有償ガチャ。それぞれが1回として数える）。
- 天井: **有償ガチャの累計が25の倍数の回**は、**未所持のモビーを1体確定**する。無料ガチャは数えない。未所持が残っていなければ、通常抽選。
- 重複は、個数として記録する（1 = 所持、2以上 = 重複）。
- 結果には、`isNew`（初めて手に入れたか）と `guaranteed`（天井による確定か）を含める。

## 作る・直すもの
1. `server/src/config/gacha.ts`: 仮のレア度・重みの設定をやめ、全モビーの均等プールと `PAID_PITY_INTERVAL = 25` に置き換える。モビーIDの一覧は、`src/petCatalog.ts` のIDと同じものを、server/ 側にコピーして持つ（アプリ本体は読み込まない）。将来ダウンロードで増えるモビーも、設定で追加できる形にする。
2. **所持の記録**: 所持数を保存するテーブル（例 `user_pets(user_id, pet_id, copies)`）を `schema.sql` に追加し、ガチャの結果を反映する。
3. `POST /pets/starter { petId }`: 最初の1体を登録する。**一度だけ**受け付ける（2回目は拒否）。所持が0のときだけ。
4. `POST /free-pulls/claim { routeId }`: 初回結願の無料ガチャを1回付与する。ユーザー×巡礼IDで冪等（同じ巡礼を2回送っても、付与は1回）。
5. `POST /gacha/pull { count: 1 | 5, kind: "free" | "paid" }`:
   - free は count=1 のみ。free の残数がないと拒否。
   - paid は count=1 または 5。有償の残数（購入で付与された分）がないと拒否。
   - 天井のカウンタは有償だけを数え、25の倍数の回に未所持を確定する。
   - 乱数は注入できる形にして、テストでは固定値で確認できるようにする（本番は `crypto.getRandomValues`）。
   - 5連は、1つのトランザクションで確定する（途中で失敗したら、どの回も確定しない）。
6. `GET /gacha/odds`: 提供割合の表示用に、全モビーと確率（均等）、天井の説明（25回ごとに未所持1体）を返す。
7. テストを追加・更新する。特に次を確認する。
   - すべてのモビーが同じ確率で選ばれる（固定の乱数で境界を確認）。
   - 有償の25回目、50回目が、未所持の確定になる。無料ガチャは天井に数えない。
   - 24回目や26回目は確定にならない。
   - 未所持が0のとき、天井の回は通常抽選になる。
   - 重複が個数に反映され、`isNew` が正しい。
   - 同じ巡礼の無料ガチャは1回だけ。無料の5連は拒否。
   - 最初の1体の登録は一度だけ。
   - 5連の途中で失敗したとき、残数・所持・天井が変わらない。

## 合わせて直す（前回のレビューで見つけた問題）
- `POST /apple/notifications` で、`appAccountToken` を通知の最上位から読んでいます。Apple の通知では、これは署名付き取引情報（signedTransactionInfo）の**中**にあります。取引の中から読むように直し、テストで確認してください。
- `POST /purchases/verify` で、取引の `appAccountToken` が、認証されたユーザーのIDと一致しない場合は拒否してください（他人の取引の流用を防ぐ）。取引に `appAccountToken` が付いていない場合の扱いは、README に明記してください。
- `POST /auth/register` に、簡単な悪用対策（同じ接続元からの登録回数の上限など、Cloudflareの標準機能で実現できる案）を README の「未実装」に、具体的な方針として書いてください。実装は不要です。

## してはいけないこと
- src/、App.tsx など、server/ 以外の変更。
- 本物の Apple 証明書・秘密鍵・トークンの生成やコミット。
- 実際のデプロイ、Cloudflareのアカウント作成、ネットワーク上のサービスへの接続。

## 完了条件
- server/ のテストと型チェックがすべて通る。ルートの `npm run typecheck` と `npm test` も通る。
- server/README.md の、仮・未実装の一覧が最新になっている。
- 意味のある単位でコミットされている（pushはしない）。
```

## プロンプト5: UIスモークテストの再実施（自動化ツールを変える）

```
あなたは「もび道」の検証担当です。ブランチ codex/v3-followups で作業してください。
前回のスモークテスト（docs/qa-smoke-20260930.md）は、ブラウザ制御が途中で切れて、27セルのうち多くが未検証でした。
今回は、接続が不安定なブラウザ操作ではなく、Playwright（Chromium の自動操作）を使い、画面ごとに独立して実行してください。

## 手順
- `npm run web` で起動し、Playwright（`npx playwright` で実行。プロジェクトの依存には追加しない）で、次の3サイズを、サイズごとに別のブラウザとして起動する。
  - 375×667、390×844、430×932
- 画面ごとに、ページを開き直して状態を作る（保存データを、localStorage の `@mobidou/journey/v1` に直接書いて再読み込みする方法で、途中の画面へ直接到達する）。長い連続操作に頼らない。
- 各画面で、スクリーンショットを `docs/qa-smoke-screens/<size>-<screen>.png` に保存し、console の error と warning を集める。
- 保存データの雛形は、docs/qa-smoke-fixtures.md に、あなたが作って記録する（体験モード用、実データ用、結願済みの再巡礼用、所持モビー複数用、途中のガチャ結果あり用）。

## 確認する画面
オープニング、ホーム（重複モビーを持つ状態も）、ホームのカード編集、巡礼の選択（イベント枠を含む）、地図、御朱印帳、コレクション、おみくじ、設定（全項目、プライバシー、もび道について）、モビー選択（ロック表示）、ガチャ画面（ひも、箱、引き上げ、結果）、結願・再巡礼の演出、プレゼント箱・友達・お知らせ。

## 合否
- 縦スクロールなしで収まる画面で、内容やボタンが切れていない、はみ出していない。
- ボタンが押せて、意図した画面へ移動し、戻れる。
- console に error がない。warning は内容を分類して報告する。

## 報告
docs/qa-smoke-YYYYMMDD.md に、サイズ×画面の表（OK / NG / 未検証、未検証の理由）と、NGの詳細（画面・サイズ・症状・スクリーンショットのパス）を書く。
コードは変更しない。修正はしない。
```
